# Отчёт. Модуль discussion и Cassandra

Отчёт фиксирует этап, на котором сообщения вынесены из PostgreSQL в отдельный модуль `discussion`. Внешний контракт publisher оставлен прежним: `http://localhost:24110/api/v1.0`, те же JSON-поля и те же коды ошибок.

## 1. Исходная точка

До этого этапа проект был одним модулем Maven. Spring Boot поднимал REST на порту 24110, Liquibase создавал в PostgreSQL схему `distcomp`, а `Message` хранился в `tbl_message` рядом с `tbl_user`, `tbl_story`, `tbl_marker` и `tbl_story_marker`. Контроллеры, сервисы и тесты уже закрывали контракт предыдущих этапов: создание, чтение, обновление, удаление, проверка длины и проверка, что история существует.

Задание требует перенести хранение `Message` в Cassandra и отделить обсуждения от publisher. Внешний API при этом менять нельзя: клиент по-прежнему видит у сообщения только `id`, `storyId` и `content`.

## 2. Как разбиралась схема

На выданной схеме у `Message` ключ партиции — `country`, а `storyId` и `id` стоят кластерными ключами. Для внешнего API это нерабочий ключ.

Поля `country` в контракте нет. Если подставить одно и то же значение всем строкам, все сообщения попадут в одну партицию Cassandra. Такая партиция становится горячей: запись и чтение упираются в один узел, а размер партиции растёт вместе со всей таблицей. Это и есть перекос данных, о котором предупреждает задание.

Второй дефект того же ключа — доступ по `id`. Публичные `GET`, `PUT` и `DELETE` знают только идентификатор сообщения. При партиции `country` строку нельзя прочитать, не зная заранее и страну, и `storyId`. Кластерный ключ сам по себе в запрос не подставляется.

Поэтому таблицу собрал не по рисунку, а по реальным запросам, не меняя JSON:

| Таблица | Ключ | Зачем |
|---|---|---|
| `tbl_message` | партиция `story_id`, кластер `id` | сообщения одной истории лежат вместе. Это запрос `GET /stories/{id}/messages`. Разные истории расходятся по разным партициям |
| `tbl_message_by_id` | партиция `id` | точечное чтение, обновление и удаление по `id`. Ключ с высокой мощностью, строки распределяются равномерно |

Колонки `country` нет. При смене `storyId` строка удаляется из старой партиции и записывается в новую: ключ партиции Cassandra на месте не обновляется. `id` при этом сохраняется.

На стороне publisher сообщение из PostgreSQL убрано. Оставлять его там и прятать фиктивную страну в отдельной колонке значило бы повторить ту же ошибку ключа уже в реляционной схеме и либо раздуть внешний JSON, либо хранить константу, которой нет в предметной области. В Postgres остаются `tbl_user`, `tbl_story`, `tbl_marker` и `tbl_story_marker`.

## 3. Разделение модулей

Корень проекта стал родительским `pom` с модулями `publisher` и `discussion`.

Publisher остался на `localhost:24110` и с префиксом `/api/v1.0`. Он по-прежнему проверяет поля и существование истории: нет истории — `40002`, короче двух символов или длиннее 2048 — `40001`. После проверки он вызывает discussion через `RestClient` по адресу `http://localhost:24130`. Связка модулей на `24110` не завязана: этот порт обслуживает только внешний API.

Discussion слушает `localhost:24130`. Проверяющий ходит на `/api/v1.0/messages`. Связка publisher с discussion идёт на `/messages` без этого префикса: в задании префикс исключён именно для связи модулей. Оба пути обслуживает один контроллер. Список сообщений истории — `GET /messages?storyId=`. Идентификатор назначает discussion, клиентский `id` при создании отбрасывается.

Проверка «история существует» осталась в publisher. В Cassandra нет внешнего ключа на Postgres, и discussion не должен ходить в чужую базу. Удаление истории по-прежнему не стирает сообщения: `GET /messages/{id}` их находит, а `GET /stories/{id}/messages` отвечает `404`, потому что самой истории уже нет.

Если discussion недоступен, publisher отвечает `50000`.

## 4. Cassandra и Liquibase

Keyspace `distcomp` создаётся до сессии Spring Data, репликация `SimpleStrategy` с фактором 1. Иначе сессия не поднимается: keyspace должен существовать раньше, чем Liquibase и репозитории.

Liquibase подключается драйвером `com.ing.data.cassandra.jdbc.CassandraDriver`. Адрес совпадает с заданием: `jdbc:cassandra://localhost:9042/distcomp`, локальный дата-центр `datacenter1`, пользователя и пароля нет. Сценарий создаёт `tbl_message` и `tbl_message_by_id`. Автосоздание таблиц Spring Data выключено, чтобы схему держал один инструмент.

Версии, с которыми это собралось: Liquibase Cassandra `4.29.1`, JDBC-обёртка `4.13.0`. Обёртка `4.14.1` в центральном репозитории Maven не нашлась, поэтому взята соседняя опубликованная версия, которая уже используется в других работах курса.

Идентификаторы — целые числа, как в прежнем API. При старте discussion смотрит максимальный `id` в `tbl_message_by_id` и продолжает нумерацию. На пустой таблице первое сообщение получает `1`.

В publisher миграция удаляет `tbl_message`, если таблица ещё есть после старых сценариев. Перед историей Liquibase соединение выполняет `CREATE SCHEMA IF NOT EXISTS distcomp`: история Liquibase пишется в эту схему, и на пустой базе схема должна появиться раньше первого changeset.

## 5. Проверка

Прогон 16.11.2026, JDK Temurin 21.0.13, Spring Boot 3.4.5.

| Модуль | Результат |
|---|---|
| publisher | 31 тест, ошибок нет. PostgreSQL для тестов — встроенный: сокет Docker на машине не отвечает |
| discussion | 25 тестов прошли, 1 пропущен |

Пропущенный тест поднимает Cassandra в Testcontainers и проверяет обе таблицы, ключ партиции `story_id` и перенос сообщения в другую историю. Без Docker он не запускается. Остальные тесты discussion проверяют сервис, контроллер без префикса `/api/v1.0`, адрес JDBC и то, что недопустимое имя keyspace отсекается до подключения.

JaCoCo по модулю discussion: 83,6% строк и 83,2% инструкций. Ниже всего покрыт цикл повторных попыток создать keyspace: он срабатывает только при живой Cassandra.

Контракт publisher на сообщениях прогнан прежними тестами Rest Assured. В них discussion подменён памятью процесса, чтобы набор не зависел от Cassandra. Отдельный тест клиента проверяет, что реальный вызов идёт на `http://discussion/messages`, без `/api/v1.0`, и что ответ `40401` доходит до publisher как есть.

## 6. Запуск

Нужны PostgreSQL на `localhost:5432` (база `distcomp`, пользователь и пароль `postgres`) и Cassandra на `localhost:9042` без аутентификации. Из корня `Zaluzhny`, при необходимости с `JAVA_HOME` на JDK 21:

```bash
mvn -pl discussion spring-boot:run
mvn -pl publisher spring-boot:run
```

Внешний адрес тот же: `http://localhost:24110/api/v1.0`. Сообщения при этом читаются и пишутся модулем на `http://localhost:24130/messages`.
